# Java Hospital — запись пациента на приём

Консольный учебный проект на Java 21 для КР 1: PostgreSQL, JDBC, Maven, два типа пользователей и запись к врачу. Интерфейс на русском языке. Данные сохраняются между запусками.

## Быстрый запуск

Требуются JDK 21 и Docker с Compose либо уже работающий PostgreSQL. Maven устанавливать отдельно не нужно: в проекте есть Maven Wrapper. Первый запуск сборки требует доступа к Maven Central.

Из папки проекта на macOS/Linux:

```bash
cp .env.example .env
# При необходимости измените пароль в .env.
set -a
. ./.env
set +a
docker compose up -d --wait
./mvnw clean package
java -jar target/java-hospital-1.0.0.jar --seed
java -jar target/java-hospital-1.0.0.jar
```

`--seed` запускают один раз на пустой базе. Он создаёт 5 пользователей и 12 записей, в том числе завершённые, отменённые, предстоящие и перенесённые. Повторная инициализация отклоняется, существующие данные сохраняются.

| Роль | Логин | Пароль в демонстрационной базе |
|---|---|---|
| Администратор | `admin` | `DemoPass123!` |
| Пациенты | `patient1`, `patient2`, `patient3`, `patient4` | `DemoPass123!` |

Вместо демонстрационных данных можно создать только администратора:

```bash
export ADMIN_PASSWORD='MyAdminPassword123!'
java -jar target/java-hospital-1.0.0.jar --init-admin
```

Потом пациенты регистрируются из стартового меню. Самостоятельная регистрация всегда создаёт роль `PATIENT`.

На Windows используйте `mvnw.cmd clean package`. Для запуска из PowerShell задайте `$env:DB_PASSWORD = 'change-me-local-password'`, запустите `docker compose up -d --wait`, затем те же команды `java -jar ...`. Файл `.env` нужен Docker Compose; Java читает переменные окружения, а не `.env` напрямую.

### Своя PostgreSQL

Создайте пустую базу `hospital` и пользователя с правом создания таблиц в ней. Настройте подключение:

```bash
export DB_URL='jdbc:postgresql://localhost:5432/hospital?connectTimeout=5&socketTimeout=15'
export DB_USER='hospital'
export DB_PASSWORD='your-password'
java -jar target/java-hospital-1.0.0.jar --seed
java -jar target/java-hospital-1.0.0.jar
```

По умолчанию используются `localhost:5432/hospital` и пользователь `hospital`. `DB_PASSWORD` обязателен. Приложение использует московское время; JDBC передаёт часовой пояс JVM PostgreSQL. Время в таблицах хранится как местное московское `TIMESTAMP`.

Схема создаётся при запуске из `src/main/resources/schema.sql`. Отдельная копия для сдачи находится в `sql/schema.sql`; их содержимое должно совпадать. Четыре врача добавляются автоматически. Изменения схемы в следующих КР стоит оформлять миграциями.

## Сценарии CLI

До входа доступны вход, регистрация и выход. После входа:

```text
1. Запись по специальности врача
2. Все записи / сортировка / действия по ID
3. Поиск записи
4. Фильтрация
5. Статистика
6. Экспорт CSV / Excel
7. Выход из программы
0. Выйти из аккаунта
```

У администратора дополнительно:

```text
8. Пользователи
9. Документация
10. Вывести таблицы базы данных
```

- **Запись:** специальность → дата → список свободного времени → свободные врачи → подтверждение. Ввод даты: `ГГГГ-ММ-ДД`. На шагах выбора `0` возвращает в меню.
- **Все записи:** пациент видит собственные записи, администратор — все. Сортировка по дате создания либо времени приёма, в обоих направлениях. Затем выбор по ID и просмотр, перенос/смена врача, отмена или удаление.
- **Поиск:** по части фамилии врача или специальности, без учёта регистра.
- **Фильтры:** статус и диапазон дат приёма включительно. Можно применять вместе, оставлять одну или обе границы пустыми.
- **Статистика:** общее число записей, каждый из четырёх статусов, активные, число перенесённых записей и общее число переносов. Администратор также видит число пользователей.
- **Экспорт:** оба формата доступны в пункте 6. Пациент экспортирует свои записи, администратор — все. Файлы имеют уникальные имена в `exports/`. CSV: UTF-8 с BOM, разделитель `;`, экранирование кавычек и защита от формул. XLSX: строковые ячейки для текста, настоящие даты, фильтр и закреплённая строка заголовков.
- **Пользователи:** администратор добавляет пациента, редактирует ФИО и удаляет пользователя без связанных записей. Удаление администраторов запрещено.
- **Таблицы:** показаны пользователи, врачи и записи; пароли и хеши не выводятся.

После операции или ошибки программа возвращается в меню. Текст вместо числа вызывает повторный запрос. Неправильные даты, отсутствующие ID, ошибки SQL и недоступность базы выводятся понятным сообщением. Завершение ввода (EOF) корректно закрывает CLI.

## Принятые бизнес-правила

1. Логин уникален, регистр не учитывается: 3–40 латинских букв, цифр, `_`, `.` или `-`.
2. ФИО: 2–120 символов, без управляющих символов; пароль: 8–128 символов. Пароль хранится как PBKDF2-HMAC-SHA256 с индивидуальной случайной солью, 210 000 итераций.
3. Пациент может читать и изменять только собственные записи. Проверка находится в сервисах, а не только в меню.
4. Записаться можно на будущий момент в ближайшие 90 дней. Клиника работает в будни с 09:00 до 17:00, начало приёма каждые 30 минут; последний слот — 16:30.
5. Нельзя занять врача или пациента двумя приёмами на одно время. Проверка защищена транзакцией, блокировками и уникальными индексами PostgreSQL.
6. «Предстоит» автоматически переходит в «В процессе» в момент начала, затем в «Завершена» через 30 минут. Актуализация выполняется при обращении к записям, без фонового процесса.
7. Отменить либо перенести можно только предстоящую запись. Отмена освобождает время. Перенос на то же время к тому же врачу отклоняется.
8. При неудачном переносе исходная запись и счётчик сохраняются. Смена врача или времени увеличивает счётчик переносов; «Перенесена» не является пятым статусом.
9. Удалить можно только завершённую или отменённую запись. Физическое удаление убирает её из статистики.
10. Пользователя со связанными записями удалить нельзя. Администраторов удалять нельзя.

В первом этапе расписание всех врачей одинаковое; отпуска, праздники и редактор расписания не реализованы. Редактирование записи — перенос даты/времени и выбор врача, без смены пациента. Редактирование пользователя — изменение ФИО, без смены логина и роли. История всех прежних дат при переносе не хранится, сохраняется число переносов. Эти решения явно ограничивают объём первой версии.

## Архитектура

```text
ConsoleUi → UserService / AppointmentService / DatabaseInspectionService
          → Repository / JDBC → PostgreSQL
```

| Пакет | Назначение |
|---|---|
| `model` | `User`, `Doctor`, `Appointment`, enum `Role` и `AppointmentStatus` |
| `ui` | Русское меню, ввод и вывод; SQL в меню отсутствует |
| `service` | Проверки прав, расписание, поиск, фильтры, сортировка, статистика |
| `repository` | SQL через Connection, PreparedStatement, ResultSet, транзакции |
| `util` | Подключение, хеширование, демоданные и экспорт |
| `exception` | Собственные бизнес-ошибки, отсутствие объекта, ошибки БД |

Инкапсуляция показана классом `User` с private final полями, конструктором и геттерами. `Doctor` и `Appointment` — неизменяемые Java records, у них также приватные поля. Полиморфизм: `AppointmentExporter` с `CsvExporter` и `ExcelExporter`; CLI вызывает один метод `export` через интерфейс. `AppointmentRepository` отделяет сервис от реализации JDBC. Использованы `List`, `Map`, `ArrayList`, `LinkedHashMap`, Stream API и Comparator. JDBC-ресурсы закрываются через try-with-resources. Значения SQL параметризованы.

ER-диаграмма: [docs/er-diagram.md](docs/er-diagram.md). Справка доступна также внутри CLI администратора.

## Проверки

```bash
./mvnw test
```

Без `TEST_DB_URL` выполняется тест хеширования; интеграционные тесты явно пропускаются. Для полного прогона нужна **отдельная** PostgreSQL-база с именем, оканчивающимся на `_test`: тесты очищают в ней таблицы пользователей и записей перед каждым сценарием.

```bash
export TEST_DB_URL='jdbc:postgresql://localhost:5432/hospital_test'
export TEST_DB_USER='hospital'
export TEST_DB_PASSWORD="$DB_PASSWORD"
./mvnw test
```

Проверяются регистрация и вход, роли и чужие ID, расписание, конфликты врача/пациента, освобождение времени, атомарность переноса, границы статусов, CRUD пользователей, поиск, фильтры, сортировка, статистика, сохранение данных при создании нового репозитория, CSV/XLSX и одновременное бронирование из двух потоков.
